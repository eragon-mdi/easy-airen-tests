# tgbot — Telegram-бот поиска по банку вопросов

Пользователь пишет несколько слов — бот находит похожие вопросы из банка `result.xml`
(формат описан в [`docs/parser/parsing.md`](docs/parser/parsing.md)), показывает их лентой
и по кнопке открывает правильный ответ.

## Запуск

```
# сначала создайте .env (переменные — в таблице ниже)
go run .               # именно `.`, а не main.go: в пакет входят несколько файлов
```

Настройки читаются из `.env` (реальное окружение приоритетнее) — все поля в `internal/cfgs/cfgs.go`:

| Переменная | Что делает |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота (обязательно) |
| `TELEGRAM_SERVER_URL` | свой адрес Bot API / прокси (необязательно) |
| `TELEGRAM_CHECK_INIT_TIMEOUT`, `TELEGRAM_POLL_TIMEOUT`, `TELEGRAM_DEBUG` | таймауты и отладка клиента |
| `TELEGRAM_RESPONSE_MIN_QUERY_LEN` | минимальная длина запроса (по умолчанию 3) |
| `PATH_QUESTIONS_FILE` | путь к `result.xml` |
| `PATH_PICTURES_DIR` | папка, **относительно которой** заданы `src` картинок (т.е. каталог с `result.xml`, а не `images/`) |
| `PATH_RENDERED_DIR` | куда складывать склеенные картинки (по умолчанию `cache/rendered`) |
| `SEARCH_*` | параметры поиска (n-граммы, пороги, бонусы) |

Пути относительные — от каталога, из которого запущен бот.

## Как это работает

```
main.go
  ├─ parser/xml      result.xml → domain.Bank (вопросы, ошибки разбора)
  ├─ storage/in-memmory  Bank → Store: вопросы в памяти + поисковый индекс (pkg/search)
  ├─ adapter/tgfinder    Store → карточки для бота; склейка картинок (imgcompose)
  └─ server/tg           Telegram-бот (go-telegram/bot)
```

Слои общаются через интерфейсы, зависимости идут в одну сторону:
`domain ← storage`, `domain ← tgfinder → server/tg`. Бот (`server/tg`) не знает ни про XML,
ни про хранилище: ему нужен только `Finder` (`Find(query) → []Item`). Адаптер `tgfinder`
превращает `domain.Question` в `Item` (текст + картинка для вопроса и для ответа).

### Старт
1. Разбор `result.xml`, загрузка в хранилище, построение поискового индекса.
2. **Пререндер:** `tgfinder.New` заранее готовит карточки всех вопросов и склеивает картинки
   в `PATH_RENDERED_DIR`. Готовые файлы повторно не создаются (ключ — версия раскладки +
   размер/время изменения исходников). Карточки держатся в памяти, поиск ничего не рендерит.
3. Запуск long polling.

### Диалог
1. Пользователь пишет текст. Короче минимума — «запрос слишком короткий».
   Ничего не найдено — «ничего не найдено».
2. Найденное группируется по одинаковой формулировке (после нормализации: регистр, знаки, «ё»).
   Если формулировок несколько — список: «Найдено вопросов: N, разных формулировок: G»,
   у каждой пометка «— K шт.»; пользователь выбирает похожую на свой вопрос (кнопки-номера,
   страницы по 8), либо «📚 Листать все подряд». Если формулировка одна — сразу лента.
   Похожие, но не совпадающие формулировки не склеиваются («открытого» ≠ «закрытого» диода).
3. Лента карточек: `◀ i/N ▶` — листание, «Показать ответ / вопрос» — переключение стороны,
   «↩ К списку формулировок» — назад.
4. На последней карточке: «✏️ Уточнить запрос» (следующий текст **дописывается** к запросу) и
   «🆕 Новый запрос». Сбросить в любой момент: `/new`, `/cancel`, `/start`.

### Скорость
- Воркеров 8 (по умолчанию в библиотеке один — все апдейты шли бы по очереди); обработка
  одного чата сериализуется, разные чаты идут параллельно.
- `AnswerCallbackQuery` отправляется без ожидания.
- Быстрые тапы по ◀/▶ не копят очередь: устаревшие нажатия пропускаются, рисуется последнее.
- Картинки после первой отправки идут по `file_id` (без повторной загрузки); id хранятся в
  `PATH_RENDERED_DIR/file_ids_<отпечаток токена>.json` и переживают перезапуск.

Состояние диалога (запрос, найденное, режим уточнения) хранится в памяти по chat ID и
теряется при перезапуске — бот тогда просит отправить запрос заново.

### Что показывается в карточке

| Тип | Вопрос (сразу) | Ответ (по кнопке) |
|---|---|---|
| `select` | заголовок и его картинки | только правильные варианты |
| `input` | заголовок и картинки | паттерны с `quality=1` |
| `match` | заголовок + левые элементы 1…N | пары «N: левый → правый» |
| `classify` | заголовок + названия групп | «группа: элементы» |

Неправильные варианты `select` и `distractors` не показываются.

### Картинки
В Telegram у сообщения одно фото, поэтому несколько картинок склеиваются в одну
(`internal/imgcompose`, только стандартная библиотека): колонка с номерами, а для пар —
строки «№ [левая] → [правая]», чтобы пары не путались. Все картинки (в том числе одиночные)
дополняются белыми полями до допустимых пропорций, чтобы Telegram не обрезал превью в чате. Файлы читаются по содержимому
(в банке есть JPEG с расширением `.png`); битые/нереальные размеры пропускаются с записью в лог.

## Ограничения
- Подпись под фото — не более 1024 символов, длинный текст обрезается.
- Сессии в памяти; один процесс.
- Исходные `result.xml` и `images/` сервис не меняет — только читает.
